When a host you own may be compromised: the evidence, the facts, and what to do next.

IR Helper runs on the host itself. It reads the evidence with a fixed list of read-only commands, finds the tell-tale facts, and proposes what to do, with the exact command and how to undo it. It never acts on its own. A person approves each step and runs it, and every step goes into a log that shows if anyone edits it later. It will not start without a written authorization naming that host.

Start here

  1. Walk through the demo below. Check the authorization, analyse a synthetic compromised host, and approve a step. Then record the log's latest hash and try to tamper with the log.
  2. On a real host, make an authorization file: node bin/ir.mjs scope-template > scope.json. Fill in who authorized it, why, and until when (30 days at most).
  3. Collect, then analyse, as root or an administrator: node bin/ir.mjs collect --scope scope.json, then node bin/ir.mjs analyse evidence.json. Nothing on the host is changed. Collect again after you act: each run is logged, so the second shows what changed.
  4. Act deliberately: node bin/ir.mjs approve F1.2 --by "Your name" records your approval and prints the command. You run it. Each step prints the log's latest hash: paste it into the ticket.

How it works

No authorization, no run. It refuses, and logs the refusal, if the authorization has no named person or purpose, has expired, starts in the future, lasts more than 30 days, or does not list this host.

Safety by construction. The list of collection commands is fixed in the code. A test fails if any of them uses a command that changes things, such as kill, rm, usermod, iptables, sc config, or PowerShell's Stop-, Set-, New-, Remove- or Disable-.

A value from the evidence, such as a process id, an address, an account or a path, is only put into a proposed command if it is in a safe form. It cannot start with a dash (an option), and it cannot hold a quote, $, %, ! or a shell operator. Anything else becomes a "check by hand" step with no command at all, so crafted evidence cannot smuggle a command in.

The log is chained with SHA-256. Editing, removing or reordering an entry breaks verification at that entry. Someone with the file could still rewrite every hash after the entry they changed, and the chain alone cannot see that. So each step prints the latest hash for you to record somewhere else, such as the ticket or an email. Checked against that hash, every entry up to it is fixed. The demo above shows both cases. Each collection's entry also records the SHA-256 of the evidence file it wrote, so the file handed to responders can be shown to be the one collected.

What it looks for

Linux

  • a process running from /tmp, /var/tmp or /dev/shm
  • a shell or netcat holding a network connection (a reverse or bind shell)
  • an account other than root with user id 0
  • five or more failed SSH logins, then a success, from one address
  • a scheduled job that runs from a temp folder, or downloads and runs code
  • an SSH authorized_keys file changed in the last 7 days

Windows

  • a process running from a Temp or Public folder
  • a scheduled task that runs from a temp folder, runs encoded PowerShell, or fetches code (mshta, rundll32, download-and-run)
  • a service running from a temp folder or a user's AppData folder
  • five or more failed logons (4625), then a success (4624), from one address

What it proposes

  • Preserve first: copy the program or file, or record its hash.
  • Contain: pause a process, lock or disable an account, block an address, disable a task, or disable and stop a service. Each comes with its exact undo.
  • Eradicate: end a process. These are marked as not reversible.

The blueprint

ir.mjs

The whole decision in one dependency-free file: the scope check, the read-only allow-list, the ten rules, the proposals, and the hash chain. Its tests are themselves tested: a mutation gate breaks the code on purpose, and every break must be caught. This page runs it byte for byte.

bin/ir.mjs

The command line you run on the host: scope-template, collect (with --dry-run to see exactly what it would run), analyse, approve, verify-log. Node 18 or later, no install.

Proven on real hosts

On every change, CI uses a throwaway GitHub Linux host and a throwaway Windows host. It plants real signs of compromise on each, checks that the tool refuses without an authorization for that host, then collects and analyses. Every planted sign must be found. Then a test script stands in for the person approving each step: it runs each proposed command and its undo on that throwaway host, and each must do what it says. The tool itself never runs one. The log must verify, and must fail once an entry is edited.

For your business

In one breath: when a machine may be compromised, the first hour decides a lot. IR Helper gives whoever is on call a repeatable first hour: authorized, evidence first, every step proposed with its undo, and every action on the record.

IT manager or on-call engineer

A checklist that runs itself: the same evidence every time, the facts with their source lines, and the commands written out. You decide and you act, with the undo in front of you.

CISO

Authorization enforced in the tool, not just in the policy. A tamper-evident record of who approved what and when, and no automated action that could make an incident worse.

Managed service provider

One method across clients' Windows and Linux hosts, with a scope file per client that names the hosts and the person who authorized the work.

Legal and compliance

The board

Security and data protection

It runs on the host and sends nothing anywhere. The evidence it gathers (process lists, logins, account names, IP addresses) is personal and sensitive. It stays in the evidence file on that host, so handle that file under your own retention policy. This page only shows synthetic data, and a file you analyse here stays in your browser.

Deployment

Keep a checkout on your admin tooling, or on removable media, so it is ready before you need it. It needs Node.js 18 or later and no network. Many servers have no Node, so carry a portable one too: Node's official zip or tar.xz runs without installing. Agree in advance who can authorize a response, and keep a filled-in scope template for each estate. Practise on a test host.

Limits, answered straight

  • Ten rules are not an EDR. It finds common, well-known signs. A careful attacker can avoid all of them, so its silence is not an all-clear.
  • A fact is a lead, not a verdict. On a fresh GitHub runner it also flags the runner's own provisioning agent, which runs from a temp folder, and the SSH keys that provisioning has just written. Both really match the rule, and both are harmless. Someone who knows the host decides.
  • Linux and Windows only. Some evidence needs administrator rights (the Windows Security log, other users' cron files). What it cannot read is listed in evidence.errors.
  • Windows task columns depend on the system language: the scheduled-task rule reads the English column names. On other languages, check tasks by hand.
  • The Linux block proposals use iptables. On hosts managed by nftables, ufw or a cloud firewall, use that tool instead.
  • Times in the log come from the host's own clock, which an intruder with full control could change. The hash you record in the ticket carries the ticket's own time.
  • Lost the authorization file? Nothing runs without one, so make a new one. The summary of every authorization used is kept in the log and in each evidence file.
  • Account steps cover local accounts. A domain or directory account is disabled in your directory, not on the host.
  • Linux SSH logins are read from the systemd journal. On a host that only writes /var/log/auth.log or /var/log/secure, check that file by hand.
  • It proposes, it does not remediate, and a proposal is not legal or forensic advice. For a serious incident, bring in responders, and hand them the evidence file and the log.
